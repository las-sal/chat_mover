## Section 1: Orientation

You're reading this because orbit is installed and you ran `/orbit:onboard`. There's nothing to verify and nothing to "overlay": orbit-spec is a **self-contained** spec-driven workflow tool — a hard fork of openspec@1.3.1 with orbit's editorial layer built into the `orbit` CLI itself.

Quick orientation:

- **CLI**: `orbit`. Run `orbit --version` to confirm it's on your PATH; it prints orbit's own version. Separately, the engine is pinned at the upstream baseline 1.3.1.
- **Workspace**: `orbit/` holds your specs (`orbit/specs/`) and in-flight changes (`orbit/changes/`). If `orbit/` doesn't exist yet, run `orbit init` first.
- **Surface**: the `/orbit:*` slash commands and their skills are generated by `orbit init` — this onboarding read is one of them.

## Section 2: Identity statement

Orbit (orbit-spec) is a spec-driven workflow tool — a **self-contained hard fork** of `@fission-ai/openspec@1.3.1`. The upstream engine and orbit's editorial/judgment layer live together in one tool, invoked as `orbit`; there is no overlay and no separately-installed CLI. The engine is pinned at 1.3.1 (deliberate, surgical upgrades only). Orbit shares concepts with upstream OpenSpec but ships an opinionated workflow with distinct disciplines, not a delta on top of upstream's defaults.

What makes orbit distinctive vs running upstream alone:

- **Editorial review** — `/orbit:review` runs a 9-pass editorial pass over the artifacts (proposal mode), a 7-pass pass over the post-apply product state (system mode, which wraps upstream's `verify-change` as Pass 0), or a 6-pass gate-less pass over an architecture doc (architecture mode — D-arc Stage D2). `/orbit:review` also carries a REVIEWER axis — who runs the pass, including a different AI (codex / fresh Claude / GPT) for a second opinion and a blind pair of two independent passes; its values and their shorthands are the review skill's to state, not this page's. Record vocabulary is frozen across the merge: the packaging emit stays `command: "review-external"`, findings stay `external-<as>-<TS>.md`. `/orbit:address-reviews` walks each finding through a structured pushback → classify → fix → ripple-cascade → remove lifecycle (works on both inline `@review:` markers and external-review findings files). Walk-mode (per-finding) is the default; `--batch` opts in. Cascade-by-default auto-applies ripple edits to IN-set files (everything outside the four lifecycle-invariant OUT categories); `--no-cascade` opts out.

- **Drift audit** — `/orbit:audit-drift` scans for drift between captured knowledge (specs, lenses, governing docs) and reality across four categories: vocabulary residue (FROM names of renamed requirements still appearing), lens staleness (perspectives or critical-paths referencing nonexistent capabilities), cross-doc consistency (CLAUDE.md / project.md disagreement with current specs), archive coherence (ADDED requirements missing from baseline, RENAMED FROM names lingering). Standalone for "something feels off" checks; auto-invoked as system-mode review Pass 6 and as a pre-archive sweep.

- **Capture (lenses)** — `orbit/lenses/perspectives.md` records named callers worth simulating from during review; `orbit/lenses/critical-paths.md` records flows worth walking end-to-end. Lenses grow organically through `/orbit:explore` capture triggers; system-mode review Passes 4-5 consult them.

- **Program architecture** — `/orbit:architect` and `orbit architecture status` (D-arc Stage D2): the cross-change declaration tier above per-change flow. Architecture docs under `orbit/architecture/` declare program stages via parseable heading conventions (`### Stage <id> — <title>` + optional `Depends-on:`/`Complete:` slots); stage state is COMPUTED from disk (which changes/explores cite the stage via `architecture: {doc, stage}` metadata), never stored. `/orbit:review --as architecture` reviews a doc (6 passes, no gate). Never a required entry point — `/orbit:explore` plus hand-editing remains first-class.

- **JSON run-summary emission via the engine emit surface** — every editorial and lifecycle command persists a JSON run summary at completion (or per chunk for `/orbit:apply`), COMPOSED AND WRITTEN by `orbit emit <command> --change <name> --payload <file>` (D-arc Stage D5): the AI supplies only the narrative payload plus the required nullable `model` provenance; the engine owns the spine, deterministic facts, computed extensions (explore counts, apply chunk/task arithmetic, `files_touched` diffing), `next_recommended`, filename + collision handling, and a strict write gate (an invalid emit is refused with NO file). Summaries persist to one of FOUR scoped locations: `orbit/changes/<name>/.orbit-runs/` (per-change), `orbit/explore/<name>/.orbit-runs/` (named explorations), `orbit/architecture/.orbit-runs/` (architecture-scoped — `/orbit:architect` and `/orbit:review --as architecture` emits, shared by all docs, never moved by change archiving), and `orbit/.orbit-runs/` (project-wide). The schema follows a universal spine with per-command extensions. (Note: `/orbit:onboard` is one of the few commands that does NOT emit — it's a reference read, not a workflow advancement.)

- **Cold-start orientation** — `orbit status` (bare = the current sprint; `--full` = the whole program) and `orbit status --change <name> --boot` (D-arc Stage D5): ordered artifact pointers in read order, the latest emit per command family with a one-sentence headline, explore-history presence, and the **Touchpoints** view — predicted (design.md's `## Touchpoints` section, authored at propose) before apply commits exist; the diff-computed ACTUAL file map (never prose) once they do. Boot is READ-ONLY and computed fresh per invocation — no hand-maintained handoff files anywhere.

- **Four execution disciplines** codified in `orbit-conventions`:
  - **Read-before-reference** (authoring-time): when generating code, specs, or docs that name a specific construct, read the actual definition first. Don't infer the shape from common patterns or training-data conventions.
  - **Change completeness** (modification-time): substantive modifications to a change-in-flight must apply fully across ALL affected artifacts before being declared done. Known residue MUST NOT be left for a downstream review to catch.
  - **Pushback** (review-time): verify each flagged issue against current state before acting. Stale findings get reported with evidence and suppressed.
  - **No-chaining** (turn boundary): the AI invokes at most the orbit workflow commands the user's message explicitly requests — one command per explicit request; it recommends, never invokes. Completing a command ends the turn at the position readout and the engine's eligibility line (`Ready when you are:`); gate `passed` means *eligible*, not *commanded*.

## Section 3: Canonical-flow walkthrough

Orbit's canonical flow is architect-first and returns to architect: an architect session plans the work, the 9 per-change phases run once per change (a stage may be served by several changes), and a closing architect session ratifies the stage and takes up the next. Each phase maps to a `/orbit:*` slash command. The flow is:

```
   architect ─→ ┌─ per change ──────────────────────────────────────────────────┐
                │ explore ─→ propose ─→ review ─→ address-reviews ─→ apply ─→   │
                │ verify ─→ review --as system ─→ address-reviews ─→ archive    │
                └───────────────────────────────────────────────────────────────┘ ─→ architect (ratify the stage)
```

**Architect (`/orbit:architect <name>`)**: Where new work starts, and where it returns. The session authors or resumes a program architecture doc under `orbit/architecture/`: its stages, its rulings, and the engine-rendered state of each stage. After a stage's changes archive, the closing session reviews the stage, ratifies it when its exits hold, and takes up the next. An architect session is never required: nothing refuses, gates or flags work that skipped one, and `/orbit:explore` remains the path for a one-off fix.

**Phase 1 — explore (`/orbit:explore [<name>]`)**: Thinking through one change, after architect. The user explores an idea, problem, or comparison; orbit acts as thinking partner. In named mode (`/orbit:explore <name>`), decisions auto-capture to `orbit/explore/<name>/explore.md` in a six-section convention (Premise / Mechanism / Decisions / Open questions / Considered & out / References). In bare mode (no name), the explore stays in conversation until 2+ substantive decisions emerge, then prompts to crystallize a name. Capture triggers also offer to save **lenses** — `perspectives.md` records named callers worth validating from during review (e.g., "API client", "Claude Desktop using MCP"); `critical-paths.md` records flows worth walking end-to-end (e.g., "First-time user adds their first device"). Lenses grow organically; system-mode review Passes 4-5 consult them.

**Phase 2 — propose (`/orbit:propose <name>`)**: Generates the change artifacts (proposal, design, specs, tasks) from the explore.md (consume mode) or from a prompted description (standalone mode). Consume mode treats `explore.md` as authoritative seed: Premise → proposal motivation; Decisions → spec deltas + design + tasks; Considered & out → design's "Alternatives considered"; References → contextual reads. Open questions become per-question prompts during propose with three resolution paths (resolve now → Decision; defer → `@review:` marker in artifacts; abandon → moves to Considered & out). After artifact generation, the staging directory at `orbit/explore/<name>/` moves to `orbit/changes/<name>/` (the historical `explore.md` persists alongside the new artifacts). Emits a completion run summary to `orbit/changes/<name>/.orbit-runs/propose-<TS>.json` ("T0" is reserved for review-external's prompt-packaging emit).

*The PR layer (D-arc Stage D6).* When `pr:` in `orbit/config.yaml` names an active regime, propose is also where the change's **draft PR** opens, so CI runs from day one and the work has an outward window for its whole life. The key takes exactly three values: `never` (the default, and what an absent key means — no PR machinery anywhere, byte-identical to pre-capability behavior), `per-proposal` (every change gets its own `<change-name>` branch and PR), and `per-architecture` (a change CITING an architecture doc rides that doc's shared program branch under one program PR; a change with NO citation falls back to per-proposal, so a standalone change never loses its window). The citation selects the target; the config only selects the regime. With no git remote or no `gh` CLI an active mode degrades to `never` behavior for that invocation and says so in one line — the lifecycle never blocks on the PR layer. READY is orbit's terminus: the archive phase flips the PR ready, and merging it is the user's act.

**Phase 3 — review (proposal mode, `/orbit:review <name> --as proposal`)**: Editorial pre-apply pass over the artifacts — 9 passes from structure/delta integrity through gap hunt to pre-handoff sweep, rolling into a 3-dimension scorecard (Completeness / Correctness / Coherence) with CRITICAL / WARNING / SUGGESTION severities. The run summary persists FIRST via `orbit emit review`; the report is then the ENGINE-RENDERED output of `orbit status --change <name> --report` pasted verbatim (D-arc Stage D4) — the tail (gate line, position, eligibility) is computed from the gate graph at render time, so the AI never authors a verdict.

**Phase 4 — address-reviews (`/orbit:address-reviews <name>` or `--from-file <path>`)**: Walks each finding (or `@review:` marker) through pushback → classify → fix → ripple-cascade → remove-marker. The classification IS the lane (D-arc Stage D4): stale findings suppress with evidence; obvious fixes are previewed compactly at triage then applied without prompts; decision-required findings get a full-prose briefing with chat-directive ratification (a closure prompt is optional and never precedes the briefing); unresolvable findings file as tasks or convert to `@todo:` / `@review(escalated):`. Ripple cascade auto-applies parallel edits to IN-set files (`--no-cascade` opts out); walk-mode is the default (`--batch` opts in). **Cross-AI loop**: `/orbit:review`'s reviewer axis reaches a different AI for a second opinion (the review skill states how the prompt reaches it and how its return is saved); the change-scoped walk discovers the saved return, and `--from-file` aims at it explicitly. Detail lives in the address-reviews and review skills (the external handoff in the review skill's `references/external-handoff.md`).

**Phase 5 — apply (`/orbit:apply <name>`)**: Implements tasks from `tasks.md` chunk by chunk. Chunks are natural pause points — at each chunk's end, `orbit emit apply` writes the run summary to `.orbit-runs/apply-<TS>.json` — chunk identity, task arithmetic, `files_touched`, and the next recommendation are all engine-computed; the AI supplies only the narrative payload. The user can interrupt between chunks. Apply pauses if a task surfaces a premise problem (e.g., implementation reveals a design issue) and prompts for direction — `@review(escalated):` markers, artifact updates, or scope cuts are all valid responses.

**Phase 6 — verify (`/orbit:verify <name>`)**: Runs upstream's `orbit-verify-change` skill — structural correctness check confirming tasks are complete, spec coverage holds, and design adherence is intact. orbit composes this as the structural gate before system-mode review.

**Phase 7 — review (system mode, `/orbit:review <name> --as system`)**: Post-apply review of the whole product state. Pass 0 wraps `orbit-verify-change` (delegated structural check). Passes 1-6: Baseline Compliance (does this change break archived `orbit/specs/` requirements?) / Cohesion (callers/dependents outside the tasks list — signature drift, ripple effects) / Surface Walk (every CLI/MCP/HTTP/public-function surface in `orbit/specs/` still coherent?) / Perspective Reviews (for each named perspective in `orbit/lenses/perspectives.md`, simulate the caller's POV) / Critical-Path Scan (for each flow in `orbit/lenses/critical-paths.md`, walk end-to-end) / Drift / Residue (invokes `/orbit:audit-drift` as a library function). Run summary persists to `.orbit-runs/review-system-<TS>.json`.

**Phase 8 — address-reviews (system-mode findings)**: Same `/orbit:address-reviews` lifecycle as Phase 4, applied to system-mode review's findings. The cross-AI external loop also works here (`/orbit:review <name> --as system --reviewer external`).

**Phase 9 — archive (`/orbit:archive <name>`)**: Moves the change to `orbit/changes/archive/<YYYY-MM-DD>-<name>/` and runs sync-specs (invokes the `orbit-sync-specs` upstream-required primitive) to propagate spec deltas (ADDED/MODIFIED/REMOVED/RENAMED) into baseline at `orbit/specs/`. Pre-archive sweeps: unresolved `@review:` marker check (prompts to address or convert to `@todo:`); audit-drift sweep (runs `/orbit:audit-drift --context pre-archive`). The per-change `.orbit-runs/` directory travels with the change into the archive, preserving the full audit trail. Run summary emits to `.orbit-runs/archive-<TS>.json` inside the archived location.

*The PR layer (D-arc Stage D6).* For a PR-attached change, archive continues past the emit as one designed **tail**: commit the archive's own writes, push, then — PER GRANULARITY — for a per-change PR, rewrite the description into an achievement landmark and flip the PR **READY**; for a PROGRAM PR (a change citing an architecture doc under `pr: per-architecture`), APPEND this stage's entry to the program PR's body and flip NOTHING — stage archives never flip the program PR; its READY flip is the human's act at arc-done, where `/orbit:architect`'s readout surfaces it alongside the merge. **MERGING IS THE USER'S ACT** — READY is orbit's terminus, and no orbit workflow or engine path ever invokes `gh pr merge`. The tail degrades gracefully at every step (no remote, no `gh`, a rejected push) with a one-line note naming what completed and what was skipped; the archive itself never rolls back. `/orbit:bulk-archive` runs no tail at all — it names any attached changes it left draft so a batch never silently strands a pull request.

## Section 5: Try-it nudge

Two paths from here, depending on what you have:

- **If you have a concrete project idea** — run `/orbit:architect <name>`. Replace `<name>` with a kebab-case name for the work (e.g., `add-user-auth`, `migrate-postgres-to-sqlite`, `redesign-archive-flow`). The architect session plans it as a program of stages; each stage then runs the per-change flow, starting with `/orbit:explore <change-name>` and `/orbit:propose <change-name>`. For a one-off fix too small to plan, `/orbit:explore <change-name>` alone is a working path.

- **If you're orienting and don't have a concrete idea yet** — run `/orbit:explore` (no name). Bare-mode explore stays in thinking-mode without committing to a change. Orbit acts as thinking partner; if 2+ substantive decisions emerge during the conversation, orbit prompts you to crystallize a name. Useful for investigating a vague concern, comparing approaches, or just orienting yourself to the codebase.

When you've gathered findings worth acting on, see `/orbit:address-reviews` to walk them. When you want a project-wide drift check, see `/orbit:audit-drift`. When you want a cross-AI second opinion, see `/orbit:review --as <mode> --reviewer external`.
